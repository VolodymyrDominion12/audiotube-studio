# NotebookLM → YouTube: план інтеграції

**Версія:** 0.3 · **Дата:** 2026-11-20 · **Статус:** етапи 1–3 реалізовано (синк, публікація, демон)

> **Що змінилося після узгодження:** до ~50 ноутбуків/аудіо (пагінація не потрібна, але
> `max_per_run` лишається); публікація починається з **приватного** режиму; **плейлисти
> відкладено** — `sync` не пише `playlist`, а `youtube.manage_playlists: false` вимикає
> створення плейлистів під час публікації. Реалізовано: `audiotube sync`, `audiotube import`,
> рекурсивний `scan`, таблиці `notebooks`/`artifacts`; далі — `daemon` з денним бюджетом,
> `flock` і systemd-юніти. Разом 113 тестів.

Документ доповнює [01_CONCEPT.md](01_CONCEPT.md) і [03_ANALYSIS_AND_NEXT_STEPS.md](03_ANALYSIS_AND_NEXT_STEPS.md).
У проєкті вже є конвеєр «аудіо → відео → YouTube». Джерело аудіо тепер теж є: `audiotube sync`
забирає перекази з NotebookLM і розкладає їх по папках-ноутбуках. Тут — як це влаштовано, що вже
працює і що лишилося до повної автоматики.

---

## 0. Коротко

**Два детерміновані етапи** в тому ж застосунку, а не два LLM-агенти:

1. **«Бібліотекар»** (`audiotube sync`) — ✅ реалізовано: читає ноутбуки й аудіоартефакти, качає
   `.m4a` у `inbox/<ноутбук>/`, пише sidecar-YAML, реєструє задачі в SQLite.
2. **«Видавець»** (наявний конвеєр + `daemon`) — транскрибує, генерує метадані, рендерить відео,
   завантажує на YouTube. Черга з бюджетом квоти й слоти — ще попереду (розділ 9).

LLM потрібен лише на кроці метаданих — і він уже реалізований. Решта — звичайний код: передбачуваніше,
дешевше, простіше тестувати й лагодити.

**Головний зовнішній ризик** — не техніка, а правила: NotebookLM не має публічного API, а YouTube
не любить масовий перезалив. Розділ 7 присвячений саме цьому; його варто прочитати до старту.

## 1. Що вже є і чого бракує

| Блок | Стан | Коментар |
|------|------|----------|
| Транскрипція (Whisper), субтитри | ✅ є | `transcribe`, `transcript.py`, SRT |
| Метадані через LLM (назва, опис, теги, глави) | ✅ є | `describe`, `planner.py` |
| Рендер 1080p + обкладинка | ✅ є | `render.py`, `visuals.py` |
| YouTube: OAuth, upload, captions, thumbnail, playlist, квота | ✅ є | `youtube.py`, `db.QuotaTracker` |
| Веб-інтерфейс, watch-folder | ✅ є | `webui.py`, `watch` |
| **Джерело аудіо з NotebookLM** | ❌ немає | треба новий модуль |
| **Папки за ноутбуками** | ❌ немає | `scan()` читає лише верхівку `inbox/` |
| **Плейлист = ноутбук** | ❌ немає | плейлист визначає LLM або YAML |
| **Планувальник публікацій** | ❌ немає | є `publish_at`, немає черги/слотів |
| FFmpeg на цій машині | ⚠️ не встановлений | `audiotube doctor` не пройде, поки не поставити |

**Важливо:** поточна модель `VideoMeta` (pydantic) не має полів NotebookLM, а `scan()` не заглядає
в підпапки. Це дві найдешевші правки, з яких починається вся інтеграція.

## 2. Архітектура

```
                    ┌────────────────────────────────────┐
   Google акаунт ──▶│ notebooklm-py (неофіційний RPC)    │
                    │ list / artifacts.list / download    │
                    └────────────────┬───────────────────┘
                                     │ id, title, created_at, duration
                                     ▼
   ┌──────────────────────────────────────────────────────────────┐
   │ ЕТАП 1 · «Бібліотекар» — audiotube sync                      │
   │  notebooks → slug-папки → .m4a → sidecar .yaml → SQLite      │
   │  ідемпотентність: artifact_id + sha256; .part → rename       │
   └───────────────────────────────┬──────────────────────────────┘
                                   ▼  inbox/<ноутбук>/<файл>.m4a + .yaml
   ┌──────────────────────────────────────────────────────────────┐
   │ ЕТАП 2 · «Видавець» — наявний конвеєр + планувальник         │
   │  transcribe → describe(LLM) → render(FFmpeg) → thumbnail     │
   │  upload → captions → playlist (опційно) → publish_at         │
   └───────────────────────────────┬──────────────────────────────┘
                                   ▼
                               YouTube
```

Розділення саме таке, а не «агент, що сам вирішує, що робити», з трьох причин:

- **Кожен етап можна перезапустити окремо.** Зламався парсер NotebookLM — конвеєр і черга живі.
- **Стан у SQLite, а не в голові агента.** Після перезавантаження комп'ютера нічого не губиться.
- **Немає потреби платити за токени там, де достатньо `if`.** Скачування й публікація — це I/O.

## 3. Доступ до NotebookLM: три варіанти

У липні 2026 Google перейменував NotebookLM у **Gemini Notebook**; сервіс той самий, старі посилання
редіректять. Публічного API для аудіопереказів досі немає — тільки кнопка «Download» в UI.

| Варіант | Як працює | Плюси | Мінуси |
|---------|-----------|-------|--------|
| **A. Вручну** | кнопка Download у кожному ноутбуці → `audiotube import <тека>` | офіційно, нуль ризику для акаунта | 30 ноутбуків × кілька кліків; немає id/дат/тривалості |
| **B. Свій Playwright** | скрипт ходить по UI, тисне Download | без сторонніх бібліотек | повільно, ламається від будь-якої зміни верстки, той самий ToS-ризик |
| **C. `notebooklm-py`** | неофіційний клієнт внутрішніх RPC | швидко, батч, є id/назви/дати/тривалість, стабільніше за UI | недокументований API; теоретично може зламатися або привернути увагу Google |

**Рекомендація: C як основний шлях + A як аварійний.** Варіант C — єдиний, що дає стабільні
ідентифікатори артефактів, без яких неможлива нормальна ідемпотентність (пункт 4.2). Варіант A
лишається завжди: команда `audiotube import` приймає теку з файлами й реєструє їх так само, тож
навіть повне блокування бібліотеки не зупиняє конвеєр.

Перевірені команди (версія 0.8.6, жовтень 2026):

```bash
uv tool install "notebooklm-py[browser]"   # або pipx install "notebooklm-py[browser]"
notebooklm login                            # один раз, у браузері
notebooklm auth check --test --json         # перевірка сесії

notebooklm list --json                      # id, title, role, created_at
notebooklm artifact list -n <notebook_id> --type audio --json
notebooklm download audio --all ./inbox/<slug>/ --dry-run   # що буде завантажено
notebooklm download audio --all ./inbox/<slug>/ --no-clobber
notebooklm auth refresh --quiet             # для cron/systemd, щоб сесія не «засинала»
```

Аудіо віддається у **`.m4a`** (AAC/MP4) — цей формат уже в `AUDIO_EXTENSIONS`, конвертація не потрібна.

> ⚠️ `notebooklm` тримає стан у `~/.notebooklm` (кукі, профіль). Для systemd задайте
> `NOTEBOOKLM_HOME` на постійну теку, інакше кожен запуск буде «неавторизованим».

## 4. Етап 1 — «Бібліотекар»

### 4.1 Структура папок

Папка = ноутбук, як і просив користувач. Slug береться з назви ноутбука, а короткий суфікс id
рятує від колізій (два ноутбуки «Docker»):

```
inbox/
  docker-za-20-hvylin-8f3c1a/
    notebook.json                                  # id, title, url, sources_count, synced_at
    2026-10-02_vstup-do-docker-4b21e9.m4a
    2026-10-02_vstup-do-docker-4b21e9.yaml         # sidecar для конвеєра
    2026-10-09_obrazy-i-shary-77c0d2.m4a
    2026-10-09_obrazy-i-shary-77c0d2.yaml
  devops-za-20-khvylyn-1a2b3c/
    ...
```

Ім'я файлу: `<дата створення>_<slug назви>-<6 символів artifact_id>.m4a`. Дата й id роблять ім'я
стабільним і сортовним; суфікс id гарантує унікальність, навіть якщо назви однакові.

`scan()` треба навчити `rglob` (зараз — `iterdir` верхнього рівня), пропускаючи `.part`, приховані
файли й теку `workspace/`.

### 4.2 Ідемпотентність і дедуплікація

Ключ ідентичності — **`artifact_id`**, а не ім'я файлу. Для кожного артефакту зберігаємо:

- `artifact_id` — стабільний id у NotebookLM;
- `sha256` файлу — щоб помітити перегенерацію з тим самим id;
- `path`, `bytes`, `duration`, `downloaded_at`.

Правила:

| Ситуація | Дія |
|----------|-----|
| Артефакт уже в базі, файл на місці, хеш збігається | пропустити (`skip`) |
| Артефакт у базі, файлу немає | перекачати (`repair`) |
| Той самий `artifact_id`, інший хеш (`--force`) | файл не чіпаємо, у звіті `changed` (версії свідомо не робимо — спека 005) |
| Артефакт зник із NotebookLM | не видаляти локально; позначити `missing` ✅ (`status --missing`) |
| Ноутбук перейменували | оновити `title`, папку не перейменовувати без `--rename-folders` |

Ніколи не перезаписуємо існуючий файл «на всяк випадок» — це головне джерело втрати даних
при збоях.

### 4.3 Алгоритм синхронізації

```
1. auth check (якщо прострочено — зупинитись і повідомити, не ламати сесію ретраями)
2. notebooks = client.notebooks.list()
   - відфільтрувати: include_shared=false → лише ті, де role=OWNER
3. для кожного ноутбука (послідовно, з паузою 1–3 с):
   a. upsert notebook (id, title, slug, url)
   b. artifacts = client.artifacts.list_audio(nb.id)
   c. для кожного аудіо:
        - якщо status != ready → skip (ще генерується або впав)
        - якщо вже синхронізовано → skip
        - dest = inbox/<slug>/<date>_<title-slug>-<id6>.m4a
        - download → dest.with_suffix(".m4a.part") → ffprobe → sha256 → atomic rename
        - sidecar YAML (title, notebook, дата)
        - register job (status=new)
4. звіт: notebooks/artifacts/скачано/пропущено/помилки; exit code 0 або 1
```

Особливості:

- **`--dry-run`** — показати план без жодного запиту на завантаження. Перший запуск робимо тільки так.
- **`--notebook ID`** — синхронізувати один ноутбук (для налагодження й ручних прогонів).
- **`--limit N`** — не більше N нових файлів за запуск (захист від «сотня за раз»).
- **Атомарність:** качаємо в `.part`, перевіряємо `ffprobe`, лише потім `os.replace`. Обірваний
  процес не лишає «битих» mp3/m4a, які потім потраплять у рендер.
- **Послідовність, не паралельність.** 3–5 одночасних завантажень не дають виграшу, зате
  підвищують шанс 429 і виглядають як бот.

### 4.4 Адаптер (єдина точка дотику до бібліотеки)

Уся залежність від неофіційного API живе в одному файлі — щоб замінити його за годину, якщо зламається:

```python
# audiotube/notebooklm.py
@dataclass(frozen=True)
class RemoteNotebook:
    id: str
    title: str
    created_at: datetime | None

@dataclass(frozen=True)
class RemoteArtifact:
    id: str
    title: str
    created_at: datetime | None
    duration: float | None
    ready: bool

class NotebookLMAdapter(Protocol):
    async def notebooks(self) -> list[RemoteNotebook]: ...
    async def audio(self, notebook_id: str) -> list[RemoteArtifact]: ...
    async def download(self, notebook_id: str, artifact_id: str, dest: Path) -> None: ...

class PyNotebookLMAdapter:          # реалізація поверх notebooklm-py
    ...
class FakeAdapter:                  # для тестів, без мережі
    ...
```

Решта коду залежить лише від протоколу. Тести ганяють `FakeAdapter`, реальна мережа — тільки
в інтеграційному тесті, який можна вимкнути змінною середовища.

### 4.5 Конфіг

```yaml
notebooklm:
  enabled: true
  profile: default            # notebooklm -p
  home: ~/.notebooklm         # NOTEBOOKLM_HOME
  include_shared: false       # чужі ноутбуки не чіпаємо
  delay_seconds: 2            # пауза між завантаженнями
  max_per_run: 20
  download_format: m4a
  repair_missing: true
```

Секрети (кукі, master-token) — тільки поза репозиторієм, `chmod 600`. `NOTEBOOKLM_HOME` у
`.gitignore`, якщо лежить у проєкті.

## 5. Етап 2 — «Видавець»

### 5.1 Sidecar: що пише «Бібліотекар»

Файл `<аудіо>.yaml` поруч з аудіо — конвеєр уже вміє його читати. Мінімум, який потрібен:

```yaml
title: "Вступ до Docker"
notebook: "Docker за 20 хвилин"
notebook_id: "8f3c1a..."
artifact_id: "4b21e9..."
source: notebooklm
generated_at: 2026-10-02
privacy: private
```

Це **не фінальні метадані**: `describe` допише опис, теги, глави, `visual_keywords`.
`privacy` переживає `describe --force` (він у списку ручних полів), а `notebook_id`/`artifact_id`
після перегенерації з YAML зникнуть — джерело істини для зв'язки «ноутбук → артефакт → задача»
це SQLite (`notebooks`/`artifacts`), тож на роботу це не впливає. Якщо колись знадобиться
зберігати їх і в YAML — треба розширити `VideoMeta`; поки що свідомо не робили.

### 5.2 Ноутбук → плейлист (відкладено)

**Поточне рішення: плейлисти не створюються.** `sync` не пише `playlist` у sidecar, а
`youtube.manage_playlists: false` змушує `publish` пропустити цей крок; статус `done` означає
«відео на YouTube», а розкладання по плейлистах робиться вручну в Studio. Щоб увімкнути
автоматику пізніше — `manage_playlists: true` і повторний `upload` для задач зі статусом `done`
(після `reset --to uploaded`).

Коли вмикатимете, правило просте: **один ноутбук = один плейлист** з тією ж назвою.

- плейлист шукається за назвою (як уже робить `Publisher`), створюється за потреби;
- перейменування ноутбука не перейменовує плейлист автоматично — це ручна дія, щоб не зламати
  посилання;
- якщо ноутбуків багато й теми перетинаються, у конфігу можна задати мапу
  `notebook_id → playlist`, щоб кілька ноутбуків зливались в один плейлист.

Черговість — FIFO за id (`daemon.order: oldest|newest`). Round-robin між ноутбуками (по одному
відео з кожного, щоб канал не був монотонним) — можливе покращення, коли з'явиться публічний канал.

### 5.3 Планувальник, бюджет і квота

Обмеження YouTube жорстке: 10 000 одиниць/добу, одне відео з субтитрами й обкладинкою коштує
~2 100 → **максимум ~4 відео на добу**, практично 2–3, щоб лишити запас на ретраї.

Тому «Видавець» — не «завантажити все», а **черга з бюджетом** (`daemon:` у `config.yaml`):

```yaml
daemon:
  interval_minutes: 30
  videos_per_day: 2
  min_hours_between: 6
  order: oldest              # oldest | newest
  max_attempts: 3
  pause_seconds: 10
  cleanup_video_after_upload: true
  quota_reserve: 0
```

Алгоритм (реалізовано в `audiotube/daemon.py`):

```
кожні interval_minutes (або один цикл з --once):
  sync (якщо notebooklm.enabled і sync_before_run)
  remaining = videos_per_day - uploads_count(сьогодні)
  if remaining == 0: вихід
  if остання публікація < min_hours_between тому: вихід
  if quota.remaining() - reserve < cost: вихід
  job = найстаріша задача new/transcribed/described/rendered (attempts < max)
  transcribe → describe → render → upload
  успіх: +1 до бюджету, .mp4 видалити (якщо cleanup)
  невдача: attempts +1; після max_attempts задача заморожується
```

Бюджет рахується за таблицею `uploads`, тому **ручні** `audiotube upload` теж враховуються.
Слоти `publish_at` поки не використовуються: відео приватні, а розклад має сенс лише після
аудиту API-проєкту. Замість нього — `min_hours_between`, щоб не вивалювати все одразу.

### 5.4 Демон і systemd

```bash
audiotube daemon --dry-run      # побачити план, нічого не робити
audiotube daemon --once         # один цикл (cron / systemd timer)
audiotube daemon                # безперервно
```

Готові unit-файли — у `deploy/systemd/`:

- `audiotube-daemon.service` — постійний процес;
- `audiotube-once.service` + `audiotube-once.timer` — цикл раз на 30 хвилин.

```bash
cp deploy/systemd/audiotube-daemon.service ~/.config/systemd/user/
systemctl --user daemon-reload
systemctl --user enable --now audiotube-daemon
journalctl --user -u audiotube-daemon -f
```

Демон бере `flock` на `data/daemon.lock`: другий екземпляр виходить з кодом 3, а не дублює
завантаження. `ExecStartPre` освіжає сесію NotebookLM (`auth refresh`), а `SIGTERM` зупиняє
процес після поточного кроку. Деталі, cron-варіант і типові проблеми — [06_AUTOMATION.md](06_AUTOMATION.md).

## 6. Дані

Мінімальні зміни в SQLite (наявна `_migrate` вже вміє додавати колонки):

```sql
CREATE TABLE notebooks (
    id          TEXT PRIMARY KEY,
    title       TEXT NOT NULL,
    slug        TEXT NOT NULL UNIQUE,
    url         TEXT,
    sources     INTEGER,
    synced_at   TEXT
);

CREATE TABLE artifacts (
    id           TEXT PRIMARY KEY,
    notebook_id  TEXT NOT NULL REFERENCES notebooks(id),
    kind         TEXT NOT NULL,          -- audio / video / ...
    title        TEXT,
    created_at   TEXT,
    duration     REAL,
    path         TEXT,
    sha256       TEXT,
    bytes        INTEGER,
    state        TEXT NOT NULL,          -- new / downloaded / missing / superseded
    job_id       INTEGER REFERENCES jobs(id),
    downloaded_at TEXT
);
```

`jobs.audio` уже `UNIQUE`, тож повторна реєстрація того самого шляху нічого не дублює. Зв'язок
`artifacts.job_id` дає змогу показати в GUI: «ноутбук → артефакт → відео на YouTube».

Додатково для демона: таблиця `uploads` (фактичні публікації — денний бюджет і `min_hours_between`)
і колонка `jobs.attempts` (після `max_attempts` задача заморожується, а не циклить вічно).

## 7. Політики, ризики, обмеження

Це найважливіший розділ: технічно зробити можна все, але частина сценаріїв має наслідки для акаунтів.

| Ризик | Імовірність | Вплив | Що робити |
|-------|-------------|-------|-----------|
| Google сприймає автоматизацію як порушення ToS | середня | блокування Google-акаунта | окремий акаунт для автоматизації; малі обсяги; паузи; ручний режим як fallback |
| Внутрішній RPC зміниться | висока (раз на кілька місяців) | синхронізація падає | пінити версію `notebooklm-py`, адаптер, `audiotube import` як обхід |
| YouTube: «inauthentic / reused content» | висока при масовому перезаливі | відсутність монетизації, обмеження каналу | додана цінність (свої вступ/висновки, глави, візуал), 2–3 відео/добу, різні теми |
| Авторські права на джерела ноутбука | середня | claim/страйк | не публікувати чужі курси/книги; приватний архів для сумнівного |
| Квота YouTube | детермінована | 4 відео/добу максимум | черга з бюджетом (5.3) |
| Аудит API-проєкту | висока для нового проєкту | публічні відео неможливі | подати на аудит або публікувати вручну зі Studio |
| OAuth refresh-токен «Testing» живе 7 днів | висока | автоматика стає щотижня | перевести застосунок у Production або переавторизовуватись за розкладом |
| Канал не верифікований | висока для нового | ліміт 15 хв, немає власних обкладинок | підтвердити телефон |
| Диск | середня | 100 відео ≈ 20–40 ГБ | видаляти mp4 після успішного upload, лишати аудіо/субтитри |

**Чесна рекомендація:** почати з **приватного архіву** (усі відео `private`, без публікації) —
це перевіряє весь ланцюг без ризику для каналу. Далі 5–10 відео `unlisted` для оцінки якості.
І лише потім — публічний канал, якщо контент справді додає цінність, а не є перезаливом
AI-подкастів. Масовий перезалив чужого AI-аудіо — найшвидший шлях до «reused content».

## 8. Тестування і критерії готовності

**Юніт-тести (без мережі):**

- `slug` ноутбука: кирилиця, пробіли, колізії («Docker» × 2), емодзі;
- `sync` на `FakeAdapter`: перший прогін качає N, другий — 0;
- обірване завантаження (`.part`) не реєструється як задача;
- артефакт без `created_at`/`duration` не валить синк;
- `scan` знаходить файли в підпапках і не чіпає `workspace/`;
- sidecar з `notebook_id` переживає `describe --force`;
- міграція БД зі старої схеми (вже є патерн).

**Інтеграційний прогін (одноразово, вручну):**

1. `audiotube sync --dry-run` → план збігається з тим, що видно в UI NotebookLM;
2. `audiotube sync --limit 2` → 2 файли, коректна тривалість через `ffprobe`;
3. повторний `sync` → «0 нових»;
4. `audiotube run --no-render` → транскрипт і YAML;
5. `audiotube render --preview 20` → подивитись очікуваний кадр;
6. `audiotube upload` одного відео як `private` → перевірити плейлист і субтитри в Studio.

**Definition of done для етапу 1:** 3 різні ноутбуки, 10+ артефактів, папки збігаються з ноутбуками,
повторний запуск нічого не дублює, звіт показує 0 помилок.

## 10. Відкриті питання

**Вирішено 19.11.2026:** до ~50 ноутбуків (пагінація не потрібна); старт у приватному режимі;
плейлисти відкладено — `sync` не пише `playlist`, `manage_playlists: false`.

**Ще відкрито:**

1. **Окремий Google-акаунт для автоматизації?** Окремий — розумніше: якщо сесію заблокують,
   особистий акаунт не постраждає.
2. **Мова аудіо?** Якщо трапляються англомовні перекази, для Whisper краще `language: auto`
   або окремий профіль, інакше укр-модель видасть сміття.
3. **Скільки відео на добу готові публікувати?** Це визначає слоти й глибину черги.

## 11. Перші команди (чекліст на завтра)

```bash
# 0. Середовище
sudo apt install ffmpeg
uv pip install -e ".[transcribe]"
audiotube doctor

# 1. NotebookLM
uv tool install "notebooklm-py[browser]"
notebooklm login
uv pip install -e ".[notebooklm]"

# 2. Пробний синк
audiotube sync --dry-run
audiotube sync --limit 2

# 3. Перевірка, що конвеєр бачить файли в підпапках
audiotube scan
audiotube run --no-render
```

Після цього стає видно реальні дані (скільки аудіо, які назви, чи є `duration`), і можна писати
`sync` уже під фактичну форму відповіді, а не під припущення.
