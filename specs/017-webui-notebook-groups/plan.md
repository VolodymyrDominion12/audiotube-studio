# 017 · План реалізації

**Спека:** [spec.md](spec.md)

## 1. Підхід

Головна сторінка перестає тягнути `/api/state.jobs`. Замість цього:

1. `GET /api/overview` — легкий знімок лічильників, файлів, квоти, конфігу й активного синку.
2. `GET /api/groups` — групи ноутбуків із лічильниками; «Без ноутбука» — для задач без
   `artifacts`.
3. `GET /api/groups/<key>/jobs` — важкі картки лише відкритої групи.
4. `GET /api/jobs?q=&status=` — плоский пошук по всій черзі, коли ввімкнено фільтр.
5. `POST /api/groups/<key>/sync` + `GET .../sync` — фоновий синк одного ноутбука.

`/api/state` лишається без змін для сумісності (spec 011) і повторно використовує той самий
знімок із параметром `with_jobs=True`.

Відкинута альтернатива — тримати всі задачі в памʼяті й лише згортати картки: не вирішує
повільну серіалізацію `job_json` (stat файлів) на кожному 15-секундному оновленні.

Відкинута альтернатива — синхронний синк ноутбука: рендер кількох відео триває хвилини-години,
HTTP-запит і браузер не мають стільки чекати. Фоновий потік + опитування стану.

## 3. Дані

Міграцій немає. Нові SQL-запити — лише читання. Фоновий прогін використовує наявні
`jobs`/`artifacts`/`notebooks` і `data/daemon.lock`.

## 4. Ризики й відкат

- **Довгий рендер** — фоновий потік, ліміт `max_per_run`, прогрес у UI; сторінка лишається
  робочою. Якщо потрібно зупинити — рестарт `audiotube web` (потік daemon, замок звільниться).
- **Кілька відкритих груп** — свідомо одна: менше запитів і компактніша сторінка.
- **Задачі без ноутбука** — окрема група `__none__`, не губляться.
- **Сумісність** — `/api/state` не змінюється; `/notebooks` не чіпаємо.
- Відкат: повернути попередній `HTML` і прибрати нові маршрути; БД не змінюється.
