# 017 · Головна сторінка: групи ноутбуків, ліниві задачі, синк ноутбука

**Статус:** implemented · **Версія:** 1.0 · **Дата:** 2026-11-28
**Залежить від:** 008, 011, 014 · **Модулі:** `webui.py`, `db.py`, `sync.py`

## 1. Проблема

На головній сторінці 241 картка задачі: сторінка довга, кожне оновлення серіалізує й малює всі
картки з превʼю, а знайти потрібний ноутбук важко. Синк зі сторінки «Ноутбуки» тягне всі
ноутбуки одразу, хоча найчастіше треба оновити один. Потрібно: згрупувати задачі за
ноутбуками, підвантажувати задачі лише для відкритої групи й мати кнопку «синк + відео» для
конкретного ноутбука.

## 2. User stories

- **US1** Як автор, я хочу бачити на головній список ноутбуків із лічильниками задач, щоб не
  гортати 240 карток.
- **US2** Як автор, я хочу розгорнути ноутбук і побачити його задачі з тими самими діями, що й
  раніше, а решта груп не заважає.
- **US3** Як автор, я хочу шукати задачу за назвою, файлом або ноутбуком і фільтрувати за
  статусом по всій черзі, а не лише в одній групі.
- **US4** Як автор, я хочу однією кнопкою для ноутбука завантажити нові аудіо й відрендерити
  відео для незавершених задач, бачачи прогрес.
- **US5** Як автор, я не хочу втратити задачі, які не привʼязані до жодного ноутбука.

## 3. Поза межами

- Публікація на YouTube з кнопки синку ноутбука: вона лише завантажує аудіо й робить `.mp4`.
- Паралельні синки кількох ноутбуків: діє той самий `data/daemon.lock`, один запуск за раз.
- Пагінація, WebSocket/SSE, нові зовнішні залежності.
- Зміна сторінки `/notebooks` (spec 015) і API `/api/state` (лишається сумісним).

## 4. Функціональні вимоги

| ID | Вимога |
|----|--------|
| GRP-R1 | `GET /api/overview` повертає `counts`, `files`, `quota`, `config` і поточний `sync` без масиву `jobs`. `GET /api/state` лишається сумісним і, як раніше, містить `jobs`. |
| GRP-R2 | `GET /api/groups` повертає групи: усі ноутбуки з БД плюс «Без ноутбука», якщо є задачі без артефакту. Кожна група має `key`, `id`, `title`, `slug`, `url`, `synced_at`, `jobs`, `by_status` (усі шість статусів, нулі включно), `published`, `errors`, `ready`, `audio_deleted`, `can_sync`. |
| GRP-R3 | `GET /api/groups/<key>/jobs` повертає задачі лише цієї групи (`job_json` + `notebook_id`, `notebook_title`). `key = __none__` — задачі без ноутбука; невідомий ноутбук → 404. |
| GRP-R4 | `GET /api/jobs?q=&status=` шукає по всій черзі: `q` — підрядок у назві задачі, імені аудіо, slug або назві ноутбука (без урахування регістру); `status` — один зі статусів, інакше 400. Відповідь містить `jobs` і `total`. |
| GRP-R5 | Головна сторінка малює акордеон груп. Відкриття групи робить один запит задач і показує ті самі картки з діями, що й раніше; одночасно відкрита одна група. Повторне відкриття бере задачі з кешу. |
| GRP-R6 | Пошук і фільтр статусу на головній працюють через `GET /api/jobs` (з дебаунсом), показують плоский список результатів; очищення фільтрів повертає акордеон. |
| GRP-R7 | Усі наявні дії картки (транскрипт, метадані, рендер, превʼю, upload, приватність, YAML, видалення/відновлення аудіо й відео) і верхні лічильники працюють без змін. |
| GRP-R8 | `POST /api/groups/<key>/sync` запускає фоновий прогін для одного ноутбука: `SyncService.run(notebook=<id>)` (нові аудіо), далі до `max_per_run` незавершених задач цього ноутбука проходять транскрипт → метадані → рендер. Публікації немає. Замок — спільний `data/daemon.lock`; зайнятий → 409. Відповідь — 202 з `run`. |
| GRP-R9 | `GET /api/groups/<key>/sync` повертає стан прогону: `status` (`running`/`done`/`error`), `processed`, `total`, `remaining`, `error`, `message`, `report`, `jobs`, останні рядки `log`. `overview.sync` містить активний або останній прогін, щоб сторінка відновила показ після перезавантаження. |
| GRP-R10 | UI показує прогрес синку в групі, блокує кнопки синку на час прогону, після завершення оновлює лічильники й задачі відкритої групи. Помилка показується в журналі, сторінка не падає. |
| GRP-R11 | Задачі з видаленим аудіо (spec 014), без файлу або з вичерпаними спробами пропускаються з поясненням у логі; відео, що вже є, не перерендерюються. |

## 5. Нефункціональні вимоги

- Головна сторінка на старті робить `GET /api/overview` + `GET /api/groups`, а не тягне 241
  важку картку.
- Один запит на відкриту групу; кеш у памʼяті сторінки; після дій і синку кеш відповідної групи
  скидається.
- Фоновий синк не тримає HTTP-запит і не блокує `/api/overview`; прогрес опитується раз на
  1,5–2 с.
- Без нових залежностей; ванільний JS; тести без мережі, FFmpeg, Whisper і LLM.

## 6. Інтерфейси

```
GET  /api/overview
GET  /api/groups
GET  /api/groups/<key>/jobs
GET  /api/jobs?q=<текст>&status=<статус>
POST /api/groups/<key>/sync          → 202 {run}
GET  /api/groups/<key>/sync          → {run}
```

`key` — id ноутбука або `__none__`.

## 8. Відповідність конституції

- **II** — групи й задачі читаються з SQLite; фоновий прогін пише туди ж, стан переживає рестарт.
- **III** — повторний синк ноутбука не качає вже наявні аудіо; рендер не повторюється для
  `rendered`/`uploaded`/`done`.
- **VI** — синк бере спільний замок, не публікує на YouTube, не перевищує `max_per_run`.
- **VII** — тести на `FakeAdapter`, без мережі/FFmpeg/Whisper/LLM; критерії покриті.
- **IX** — інтерфейс і повідомлення українською.

## 9. Відкриті питання

Немає. Свідоме рішення: кнопка рендерить, але не публікує; обмеження — `notebooklm.max_per_run`
задач на один запуск, решта лишається в черзі з повідомленням.
